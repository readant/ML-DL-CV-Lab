## 为什么技术点要单独成篇

**项目会换，技术点不会。**

只在一个项目里学会的实现，换个任务就用不上——你会知道「这个项目里这么写」，但不知道「这类问题该用哪种技术」。把技术点从项目里抽出来整理，才能迁移。

规则：**每个技术点独立成篇，不绑定任何项目。** 项目只在「能用在哪」一栏出现，作为例子，不是主体。

## 什么算「技术点」

同时满足四条才算：

1. **有明确来源** —— 能指到具体论文或经典实现，不是自己临时写的
2. **能单独替换或去掉** —— 且去掉后结果会变（这条最硬）
3. **有最小实现** —— 50 行以内能跑通
4. **能一句话说清解决什么问题** —— 说不清就是没理解

**不算技术点的**：框架 API（`DataLoader`、`argparse`、`logging`）、训练循环、超参调优技巧、工程组织方式。这些是脚手架，去掉只是跑不起来，不会让方法变差。

## 选型指引：按你要解决的问题找

这张表比逐个读文档更常用。先定位你的问题，再跳转。

| 你的情况 | 选它 | 理由 |
| :--- | :--- | :--- |
| 输入是一维特征向量，某些列明显比别的列有用 | **A1 SE** | 最轻，几乎零成本，先试这个 |
| 输入有天然的语义分组（如"状态量 / 导数量"），想知道哪一组更重要 | **A7 分组注意力** | SE 只能到列级，分不清"组" |
| 有两个来源的信息，要让它们相互参照 | **A4 交叉注意力** | 一路出 query，一路出 key/value |
| 一路信息要整体控制另一路的计算强度 | **A5 FiLM** | 比交叉注意力轻得多，常常够用 |
| 有多个实体/位置，它们之间需要交互 | **A3 自注意力** | 序列建模的标准答案 |
| 只想增强非线性表达，不涉及信息融合 | **A6 门控** | 不是注意力，但常被归在一起 |

**默认从 A1 或 A5 开始**：参数量小、实现短、失败代价低。交叉注意力和自注意力留到前两个不够用时再上。

## 每个技术点的固定结构

统一六节，便于横向对比：

1. 解决什么问题（痛点）
2. 机制（用图和数据流讲，不推导公式）
3. 形状怎么变（输入什么、输出什么、中间是什么）
4. 最小实现（可直接跑的代码）
5. 变体与对比
6. 何时用 / 何时别用

## 怎么用这组笔记

1. **不要从头读到尾。** 先看「选型指引」，定位当前问题，只读对应的那一篇。
2. **每篇的最小实现要亲手跑一遍。** 跑不通就说明没读懂。
3. **跑完改一个数字**（比如把压缩比从 16 改成 4），看输出怎么变——这是验证理解最快的方法。
4. 用过的技术点，在自己的项目笔记里记一行「用了 A1，因为……」，积累成自己的判断。
